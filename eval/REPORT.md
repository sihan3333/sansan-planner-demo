# 指令解析评测报告 · 2026-10-24（种子集基线）

## 设置

- **用例**：60 条，全部是开发者编写的种子用例（`author: seed`），覆盖 14 类指令：新增（具体时间 / 只说时长）、删除、挪动、改时长、顺延、重排、多个指令、改模板、新建项目、记进度、改项目、删除项目、无关的话。
- **固定场景**：一天的日程（当前时间 14:00，上午的活动大多已完成，「背单词」没做）、基础模板、4 个学习项目。
- **对比对象**：DeepSeek（经 Cloudflare Worker 中转，temperature 0）与本地规则（正则 + 关键词）。两者的输出都先经过同一套校验（对象必须真实存在、时间格式正确）。
- **判分**：一句话产生的指令必须全部对上才算对，不能多也不能少。

## 失败分析

**DeepSeek（1 条）**

- #18「数据分析改到晚饭后」→ 挪到 18:00（晚饭开始），应为 19:00（晚饭结束）。**参照物理解成了开始而不是结束**。可以在提示词里明确「X 后 = X 的结束时间」，再用新的说法复测。

**本地规则（11 条），按原因归类**

| 原因 | 用例 | 说明 |
|---|---|---|
| 不支持参照物 | #18、#21「晚饭后」 | 规则只认具体时间，不会去查「晚饭」几点结束 |
| **回归 bug** | #28「把今天没做完的往后排」 | 「往后」命中了「改模板」的触发词（以后 / 往后），被当成改模板，重排被跳过。统一入口改造时引入；界面上的按钮不受影响，但打字说这句话会失败 |
| 上下午推断 | #19「提前到七点」 | 没说上下午的 7 点被当成早上 7 点；规则只把 1–6 点默认成下午 |
| 一句话里重复说时长 | #2「…大概半小时」、#4「…，一个小时」 | 逗号后的时长被拆成第二条「新增」 |
| 说法没覆盖 | #22「只读半小时」、#42「100道」、#43「新建一个学习项目：…」、#54「总共其实是120集」、#56「项目删了吧」 | 关键词或单位不在规则里 |

## 评分口径的两处调整

第一轮有 3 条 DeepSeek 失败，逐条复核后，其中 2 条是标准答案过严，改为接受所有合理答案：

- #41「两周内读完」：截止日按含今天算是 13 天后，按满 14 天算是 14 天后，两种都接受。
- #42「100道SQL题」：单位写成「题」或「道」都接受。

调整前 DeepSeek 为 57 / 60（95.0%），调整后 59 / 60（98.3%）。本地规则不受影响。

## 修复记录

- **#28 回归 bug（已修复）**：判断「改模板」的触发词改为只在句首出现「以后」，或者「以后 / 往后」后面紧跟「每天 / 都 / 就」时才算。修复后本地规则 **50 / 60（83.3%）**，其余 10 条失败与修复前完全相同，没有引入新错误。另外用 6 句评测集以外的说法确认：「往后每天加30分钟冥想」「以后每天都不散步了」「以后晚饭改到六点半」仍改模板；「晚饭以后去健身一小时」「下班以后约朋友吃饭两个小时」改为正确地只改今天（修复前会被误判成改模板）。
- 这次修复只影响本地规则，DeepSeek 不经过这段判断，结果不变。
- 注意：#28 本身在这份评测集里，修复后它的通过不能算作「泛化」的证据，需要在新的一批说法上继续验证。

## 局限与下一步

1. **种子集有偏**：用例和本地规则出自同一人，本地规则的分数偏高；DeepSeek 的提示词也是同一人写的。**对外引用的准确率应来自真实用户的说法**：请 5–10 位同学各写 10 句「想怎么改日程 / 记学习进度」，标成 `author: "user"` 后重跑，只看这部分的结果。
2. **不在同一批用例上调参**：上面的失败如果直接针对这 60 句修，分数会虚高。修复后要在一批新的说法上复测。
3. **建议下一步修的**：DeepSeek 的「X 后」参照物理解（#18）。
